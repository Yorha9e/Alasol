# 包边界：每个包的存在理由与变更轴

> 目的：为每个包写清「**它为什么存在**」与「**什么变化会导致它变**」。
> 关键：**「什么不会导致它变」才是边界的真正定义**——它把"这个改动该放哪"变成可机械检查的问题。
> 状态：提案，待审。

---

## 0. 一句话总纲

> **一个包只应该因为一类变化而改。凡是第二类变化要改它，说明边界画错了。**

---

## 1. 包清单

| 包 | 它为什么存在 | 什么变化会导致它变 | 什么**不会**导致它变 |
|---|---|---|---|
| **`contracts`** | 跨进程 / 跨语言 / 跨时间流动的所有数据，只在这里定义一次（JSON Schema 优先，codegen 产出 Go 类型） | 新增一种跨边界消息；字段语义变更；字段可空性变更 | 换 provider、加一个工具、加一个工作流、换存储引擎、换模型 |
| **`core`** | agent 的骨架逻辑——loop、事件总线、策略链、上下文装配、扩展注册、发现表、**门禁判定**、**重试控制流**；**只定义能力接口（exec / fs / net / proc），不含任何 I/O 实现**，因此可被任意宿主嵌入与单测 | 新增一种生命周期状态；改变事件的触发条件；改变策略求值顺序；**新增一类能力接口** | 换存储、换 provider、换模型、加 UI、改传输协议、加一个工具（**在已声明能力内的**工具） |
| **`runtime`** | core 定义的那些接口在真实世界里的实现——SQLite 存、进程起、沙箱落、provider 调、网络走；**门禁的执行侧**（快照 worktree、跑命令）；**索引器**（派生表的唯一写者） | 换数据库实现；换沙箱后端；换 provider SDK；换进程管理方式；换门禁执行方式 | core 的语义变化、加 UI、加一个工具、工作流内容变化 |
| **`host`** | 唯一的组合根 + 传输入口——把 core 与 runtime 装配起来，并对外暴露 stdio / WS+NDJSON | 加一种传输；新增一个入口二进制；改装配方式 | 业务语义、core 内部结构、runtime 的具体实现选择 |
| **`ui/tui`** | 把事件流渲染成人能操作的东西 | 加面板；改快捷键；换 TUI 库；改交互方式 | 它**不判断任何语义**，只渲染 core 给出的结论 → 任何"判断"变化都不动它 |
| **`extensions/*`** | 把一类具体能力打包成**可独立分发、可独立替换**的单元；它们是"core 的实现"，不是"core 的一部分"；**里程碑部件（`MilestoneHandler`）归此类**（W14） | 这一类能力的具体做法变了（换 bash 工具实现、改策略规则集、加一个 provider、加一个里程碑部件） | core 的接口、宿主形态、工作流契约 |
| **`workflows/`** | 工作流是**数据**（能力包 + 批准）；把它从代码里独立出来，才能被用户写、被 agent 组合、被分发。**代码部件一律在 `extensions/`**（里程碑部件、CI 执行器），本目录只放定义 | 工作流**契约的字段**变了（那属于 `contracts` 的改动） | 单个工作流的内容变化是**数据变化，不是代码变化** → 不进 git 代码路径的语义评审 |
| **`sdk`** | 给外部宿主一个稳定的最小入口——"我要在你的 harness 里跑一个 agent" | 对外承诺的用法变了 | 内部重构 → **这正是它存在的意义：隔离不稳定性** |
| **`cmd/*`** | 可执行入口的薄壳 | 命令行表面变了（加子命令、改参数） | 一切逻辑 → 都在 core / runtime |
| **`internal/`** | 不打算对外承诺的实现细节，允许随时改 | 任何时候 | —— |

## 2. 依赖规则（硬约束，可机械检查）

```
cmd/  →  host/  →  core/  →  contracts/
          │         ↘  runtime/  →  core/(接口)  +  contracts/
          └────────────→ ui/tui/          （cmd 负责装配 TUI）
ui/   →  contracts/            （不 import core）
extensions/* → contracts/ + core 的接口    （不 import runtime 的具体实现）
```

**装配关系（谁实例化谁）**：
- `cmd/` 实例化 `host/`（组合根），并装配 `ui/tui`（TUI 是入口的一部分）
- `host/` 实例化 `runtime/` 的实现并注入 `core`
- **审批 UI 的落点**：`Approver` 是 core 的进程内接口，**审批请求/答复是跨边界消息**（D21 清单）→ TUI 通过 `Transport` 桥接，`extensions` 不 import `ui`，`ui` 不 import `core`
- **进程级扩展的加载器**要起进程（属 runtime），但**注册表在 core** → 通过 core 定义的"能力接口"调用 runtime，不反向依赖

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **`core` 不得 import `runtime` / `extensions` / `host` / `ui`** | 可测性铁律：core 的单测不需要任何真实 IO |
| 2 | **`contracts` 不 import 任何内部包** | 契约要能被任何语言独立消费 |
| 3 | **`runtime` 实现 core 的接口；core 只定义接口** | Go 惯例：接口由消费方定义 → 依赖方向天然向下 |
| 4 | **`ui` 只依赖 `contracts`** | 前端语言自由（TS / Rust / Python 都能接） |
| 5 | **`extensions` 依赖 contracts + core 的接口，不依赖 runtime 的具体实现** | 否则扩展就把实现焊死了 |
| 6 | **跨边界的类型只能在 `contracts` 定义**；core / runtime 内部类型不得外泄到边界 | 防止"内部类型悄悄变成公共契约" |
| 7 | **依赖单向传导**：改 contracts → 可能要改 core/runtime；改 core 接口 → 要改 runtime；改 runtime → core 不动 | 这就是"变更轴"在依赖图上的投影 |

## 3. 三个容易腐化的边界点（重点盯）

| 边界 | 腐化方式 | 防线 |
|---|---|---|
| **core ↔ runtime** | core 里出现 `*sql.DB`、`*exec.Cmd`、具体 provider SDK 类型 → 边界消失 | lint 禁止 core import runtime / 第三方 SDK |
| **core ↔ ui** | UI 里出现"怎么判断该不该执行"这类逻辑 → 判定被复制成两份 | UI 只渲染 core 产出的 `Decision` / `ContextSnapshot` / 事件 |
| **contracts ↔ 内部** | 内部结构体被直接序列化 → 契约随实现漂移 | 只有 contracts 里的类型允许出现在跨边界载荷中 |

## 4. 审阅清单（给审核 session 逐条验）

对每个包回答：

- [ ] 它的一句话是否说清了**存在理由**（而不是"装了什么"）？
- [ ] **变更轴**是否只含一类变化？有没有把两类混进一句？
- [ ] 第三列（**不会**导致它变）是否真的成立？——抽查 3 个假想改动，逐条判它落在哪个包
- [ ] 有没有**别的包**也会对同一类变化有反应？（= 边界重叠）
- [ ] 有没有某类变化**不属于任何包**？（= 边界空洞）

全局检查：

- [ ] 依赖图里有没有**环**？
- [ ] `core` 能不能在**没有 runtime 的情况下**跑完它的单测？
- [ ] 一个**只想读事件流**的外部程序，能不能只依赖 `contracts` + 一份 JSON Schema 就实现？（跨语言中立性验证）
- [ ] `extensions` 能不能被**单独发版**而不动 core？
- [ ] 有没有哪个包的**一句话是空的**（"它装 X"）？→ 那是还没想清楚存在理由

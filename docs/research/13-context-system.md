# 13 · 上下文系统（级联压缩单元）——候选设计

> **状态：⏸ 候选，待验证**（2026-10-28 讨论稿）。这是"预备单位"：**能力组件，可挂可不挂**——
> 不挂时主调度跑最普通的 `append` 兜底；出现"单 agent 长期工作"或"调度侧分期"的工作流时再挂载。
> **转正条件**：v1 真实多 session 工作负载跑出数据（增长曲线 / 切后回捞率 / 沟通-工作量比 / summary 够用度）后复审。
> **未进 `07`**（不制造既成事实）；相关决策引用 J 系 / X6 / F5 / J15，不重抄（D21）。

## 1. 定位与教训

- 本单元从"单 agent 从头做到尾"的形态里长出来（一线执行的线性工作语义清晰）；多 agent 协作侧的沟通流不能硬套阶段切分——**这是 2026-10-28 讨论纠正的错配**（设计者与用户都一度错配）。
- 因此它做成**独立能力组件**：长程单 agent 工作流用它；调度侧主上下文先用 append；调度侧需要分期时按 §3 的"通过点"分期挂它。
- 多套上下文系统**按 agent 各挂一套**（一个 agent 内不混用），套间由 agent 边界天然隔离；装配（Assembler/Compactor）各挂各的实例；**运行期不切换**。

## 2. 三型映射（按工作形态）

| 型 | 谁 | 系统 |
|---|---|---|
| 一线型（从头做到尾） | worker | 本单元（阶段式 tiered） |
| 调度型 | main / orchestrator | 一期 append；分期需求出现后按 §3 挂本单元 |
| 短命型 | 单发 helper | append，永不压缩 |

## 3. 阶段边界 = 验证通过点

阶段不是 token 区间，是**工作的关节**：一次验证循环的通过时刻（如 critic→reviewer 循环出 `VERDICT: clean`、gate receipt 通过）= 一个阶段的结束。软边界 = agent 显式 tier 标记（J11 机制）。**水位只当兜底护栏，不是主触发**（主触发=阶段关节）。

## 4. 保留策略：不可变阶段尽量留存，预算驱动降级

**已完成的阶段是不可变的 → 它是 prompt cache 的好朋友（重写才毁缓存，留存不毁）。** 压缩不是阶段边界的仪式，是预算淘汰：

```
进入阶段 N：N-1 保持全文 → N-2 降 L1 → 更老降 L2（最老先降）
只往一个方向：全文 → L1 → L2，永不回升；预算告急才提前降级
```

留比问便宜（recall 一次 ≈ 一轮 loop ≈ 30k），所以跨阶段连续性优先靠全文/L1 就地满足。

## 5. 两级压缩 + recall 工具

| 级 | 内容 | 残留 |
|---|---|---|
| L1（浅） | 摘要**含具体工程操作** + 指针 → 持久化原文 | ≈3k/阶段 |
| L2（深） | 小阶段结论 + **一根指针** → 持久化原文 | ≈0.7k/阶段 |

- **`recall(ref)` 工具**：LLM 可调用取回原文（= J15 指针解析 `Resolve(ref)` 的工具化形态）
- **指针语义显式化**：二级条目自带使用说明——`【阶段 5 · 结论：…】现场细节已存档，调用 recall("stage:5") 取回全文`；ref 用阶段号（`stage:N`，给 LLM），seq 区间给机器
- 级联规则（防关联腐坏）：**压缩输入 = 账本 + 被压区间全文**（永不读别的阶段摘要）；**refs 只指原文、永不指摘要**；预算是唯一全局耦合

## 6. 常识区（共享代码/知识）与缓存定律

重复阅读的公共内容（同一段代码的结构等）收进**常识区**，位置在**热区最前**：

```
[前缀·永不动][ledger 稳定半·罕变][L2 区][L1 区][常识区·偶变][当前工作区·每轮在变][尾部]
                                              ↑ 变化的东西聚在"生长前沿"
```

**缓存定律：易变内容贴着生长前沿放，稳定内容永远在最前。** 常识区/ledger 易变半（已完成/待解）都贴前沿，失效范围压到最小（只废工作区缓存，而工作区缓存本来就每轮不保）。常识区更新随阶段完成一起做（与 ledger 更新同拍——X6）。

## 7. 兜底三级 + 预防

1. **全部 L1 → L2**（便宜、可回捞，先做）
2. **切当前阶段**（劈成小段按两级压）——激进但合理；走到这步 = **orchestrator 阶段切大了**（上游错误，不是压缩的错），兜底触发本身就是诊断证据
3. **预防**：prompt 明示 orchestrator"阶段不能过大" + 框架侧硬预算告警（阶段工作区超预算发事件）双保险

## 8. 预算数学（口径：两阶段合计 ≤300k → 单阶段 S≤150k；一轮 loop ≈30k → 一阶段 ≤5 轮）

布局：`[前缀 15k][常识区 30k][历史区][当前阶段 ≤150k][尾部 10k]`；历史区预算 = W − 205k

| 窗口 W | 历史区 | 尽量留存策略下可追溯 |
|---|---|---|
| **1M** | ~795k | 全文 4-6 个 + L1 3 个 + L2 数百个（阶段典型 100-150k）→ **百级阶段** |
| **256k** | ~51k | 全文 0-1 个 + L1 3 个 + L2 ≈60 个 → **约 60 阶段** |
| **200k** | **负 5k，不成立** | 硬约束发现：**本设计要求 W ≥ 256k**（或阶段压到 ≤130k / 常识区让位） |

阶段预算法则：**S ≤ W/3**（1M → 300k 上限的来源）；超预算触发 §7 预防告警。

## 9. 转正前必须回答的（v1 数据裁决）

1. 真实长程多 agent 会话里沟通量 vs 工作量几比几？orchestrator 上下文实际构成？
2. 撞墙被切掉的内容事后被要过几次？（验证"上下文内不保存、回捞走 recall"）
3. L1/L2 的摘要实践中够不够用？recall 使用频率？
4. 阶段关节在真实工作里清晰吗？（阶段平均大小分布 vs 预算）
5. 更根本的：单 agent + 好上下文能覆盖多少本想交给多 agent 的活？（对照组试验）

**验证载体**：v1 hub（多 session/多管理真实落地）+ `context.assembled` 每轮落库（现成观测仪器）+ query/model 事件入流（v1-S1 补）。
